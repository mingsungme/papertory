## 2. 문제 정의 & 가설 수립

**핵심 메시지:** "업무 우선순위·일정 관리"라는 PM 역할을, 문제를 구조화하고 팀의 가설을 세우는 과정으로 재해석.

**들어갈 내용:**
- 기획 배경 3가지 흐름: SNS발 새로운 뉴스 소비, 노션/엑셀식 기록 열독, 한경 디지털 트래픽 감소
- 문제 정의 4가지: 저조한 체류시간 / 성장으로 안 이어지는 소비 / 활용 안 되는 스크랩·하이라이트 / 신규 유입 경로 부재
- "신규 유입 경로 부재"는 감이 아니라 데이터 근거 있음 — 한경 내부 Looker Studio 자료(비공개)에서 리텐션·이탈률 문제 확인, 공개 분석에서는 유튜브 7채널 합산 구독자 약 390만 명이라는 큰 잠재 독자층이 실제 원문 기사 세션 유입으로는 거의 전환되지 않는 구조적 갭 발견 → 슬라이드 4에서 데이터로 이어서 보여줌
- 핵심 가설: "뉴스 소비가 '기록 루틴'이 될 때 재방문이 생기고, 이게 자발적 공유로 신규 유입까지 이어진다"

## 4. 사용자 리서치 — 실제 유저 × AI 페르소나 이중 검증

**핵심 메시지:** 이 프로젝트에서 가장 차별화되는 리서치 방법론. "실제 사람 인터뷰"와 "합성 페르소나 LLM 인터뷰"를 교차 설계했다는 점을 강조.

**들어갈 내용 (리서치 트랙이 3개로 나뉨 — 혼동하기 쉬운 지점이라 명확히 구분):**
- ① 한경 실무자 인터뷰·피드백: 이 프로젝트 자체가 "한경 도메인을 개선하는" 과제였기 때문에, 신규앱 MVP를 구상하는 과정에서 한경 관계자들과의 실제 인터뷰·피드백(저널리즘 DX/AX 논의)을 거쳐 기회요소를 도출
- ② **실제 FGI (사람, 20~30대 여성 5명):** MVP 데모가 아니라 **게이미피케이션 POC들(재판·머니워크·3D펫·3D하우스 등)을 시연해 "게이미피케이션이 학습을 돕고 유입으로 이어질 것이다"라는 가설을 직접 검증**한 세션. 게임형 3종은 회의적, 실용형 4종은 즉시 호평 → 현장 사진 있음
- ③ **AI 페르소나 챗봇 시뮬레이션 (fgi_chatbot_free.html):** 서담채·손승호·강종희·조기원 4개 페르소나에 각각 system 프롬프트를 부여해 FGI 토론을 시뮬레이션하는 도구를 직접 만들어, 실제 FGI를 보완/확장하는 용도로 반복 탐색. [페르소나챗봇_FGI_요약.md](docs/deliverables/analysis/페르소나챗봇_FGI_요약.md)는 이 시뮬레이션 결과 정리 문서 — "강종희" 페르소나의 "캐릭터 키우는 재미보다 내 돈 불어나는 게 눈에 보여야" 발언은 이 AI 시뮬레이션에서 나온 것. **다만 실제 FGI(②)에서도 "보상이 자산형성에 도움돼야 쓸 것 같다"는 취지의 발언이 실제로 나왔음** — AI 시뮬레이션과 실제 사람 반응이 같은 방향으로 수렴했다는 게 이 리서치의 신뢰도를 보여주는 지점
- ④ **Nemotron 페르소나 파이프라인 (별도 트랙):** nvidia/Nemotron-Personas-Korea(약 100만 명 합성 데이터셋) → "경제·자기계발·성장" 키워드 SQL 필터링 → 페르소나 '송소라' 도출 → LLM 챗봇으로 반복 인터뷰. 핵심 인사이트: 능동적 스크랩에 흥미, 꾸미기 리워드는 실질 혜택 필요, '내 지갑 번역기'에 강한 호감
- ⑤ 채널·트래픽 데이터 분석: 한경 내부 Looker Studio 자료(비공개, 수치 미표시)로 리텐션·이탈률 문제 정량 확인 + 공개 유입경로 통합분석에서 유튜브 합산 구독자 약 390만 명이 원문 유입으로 거의 전환되지 않는 구조적 갭 발견 → '방송기사 모아보기' 기획으로 연결

**근거:** [페르소나챗봇_FGI_요약.md](docs/deliverables/analysis/페르소나챗봇_FGI_요약.md), [fgi_chatbot_free.html](docs/deliverables/persona/fgi_chatbot_free.html)(AI 시뮬레이션 소스), 발표스크립트 p.8·p.20–22, [kms_형광펜poc.md](docs/deliverables/poc/kms_형광펜poc.md)("저널리즘 DX/AX 논의에서 나온 UI 개선 기회요소"), [채널별_유입경로_통합분석_1.md](docs/deliverables/analysis/채널별_유입경로_통합분석_1.md)
**확인 필요:** 실제 FGI(②)에서 "자산형성에 도움돼야 쓸 것 같다"는 정확한 워딩·발언자 — 정확한 인용문으로 대체할지 확인. AI 시뮬레이션(③)에 쓴 실제 진행자 질문(쿼리) 예시도 슬라이드에 넣을지 확인
**캡처 후보:** 26.7.31 멘토링 피드백에서 "데이터 기반 디자인 경험을 별도로 부각하라"고 명시 → [2026.07.31_멘토링_피드백_정리.md](docs/meeting-notes/2026.07.31_멘토링_피드백_정리.md). Looker Studio 내부자료는 **공유 불가 — 슬라이드에 수치·스크린샷 절대 넣지 말 것**, 인사이트만 텍스트로 서술. 유입경로 통합분석 쪽은 공개 문서라 표/차트 캡처 가능

## 6. 손으로 만든 증거 — 바이브 코딩 POC + 실제 배포 코드 기여

**핵심 메시지:** PM이 관리만 한 게 아니라, 실제 UX 플로우를 코드로 만들고 검증했다는 가장 강력한 반증 자료.

**들어갈 내용:**
- POC_2 — 형광펜 하이라이트 → 액션아이템 내보내기: 실제 react-app 컴포넌트(ArticleHeader/Article/Sidebar) 이식, 하이라이트→액션시트→카드 내보내기→공유→스크랩까지 전 구간 구현, 페이월-결제 연동까지 재현
- POC_5 — 기사→재판 진입 시나리오: "기사를 읽는 행위 자체가 게임 준비가 되는" 구조로 설계 전환, 스크롤 기반 증거 수집 + 왕복 루프(게임 종료=기사 복귀) 설계
- 두 POC 모두 브라우저 자동화(`preview_eval`)로 전 구간 DOM 검증까지 직접 진행
- 배포된 MVP 코드베이스에도 직접 커밋 71건+ (a11y aria-label 추가, 완료 미션 UI, 글래스모피즘 토큰화, 스크랩북 펜 UI 등) — POC를 넘어 실제 프로덕트에 기여
- **디자인 토큰 거버넌스 — 글래스모피즘 통합 사례:** 플로팅 UI(툴바·FAB·상단바)에 쓰는 유리 표면 효과가 컴포넌트마다 그라디언트·그림자 값이 제각각 인라인으로 흩어져 있던 것을 발견 → `--pt-glass-*` CSS 변수 + `.pt-glass` 유틸 클래스로 통합(커밋 `fcb57bf`), "플로팅 요소에만 적용·정적 카드엔 금지"라는 사용 원칙까지 design.md에 명문화. 토큰을 "정의"만 한 게 아니라 실제 코드에 **일관되게 적용됐는지 감사하고 드리프트를 고친** 역할

**근거:** [kms_형광펜poc.md](docs/deliverables/poc/kms_형광펜poc.md), [kms_재판poc.md](docs/deliverables/poc/kms_재판poc.md), `git log` (Minseong 계정 커밋 이력), [Papertory/guidelines/design.md](Papertory/guidelines/design.md) "Glass Effect" 절 — "개별 컴포넌트에 직접 인라인하지 말 것(제각각 값이 흩어졌던 이유)"라는 문구가 before/after의 직접 증거

- 이름 '페이퍼토리' = Paper(한경의 신뢰감 있는 레이아웃·몰입감의 디지털 전환) + Story(기록이 쌓여 나만의 성장 이야기가 됨)

- 컨셉 문구: "다람쥐가 도토리를 성실히 주워 겨울잠을 대비하듯, 뉴스를 매일 읽어 경제 감각을 만듭니다"

## 8. 협업 리더십 — 프로세스 진단 & 도구 재설계

**핵심 메시지:** 문제를 진단하고, 콘텐츠 성격에 맞춰 도구를 분리 설계한 시스템 사고.

**들어갈 내용:**
- 07.24 회고에서 진단한 문제: 지라·클라우드 활용 미흡, 디펜던시로 인한 업무 몰림, 파일 접근 권한 문제
- 해결책을 용도별로 도구 분리 설계:
  - **Git/GitHub** — 코드·POC·MD 문서 등 버전 관리가 필요하고 실제 개발 과정을 증명해야 하는 것 (커밋 히스토리·PR 머지 이력이 곧 개발 과정의 증거)
  - **구글드라이브** — PRD·영상·이미지·결정사항·발표자료 등 비개발 팀원도 접근성 있게 봐야 하는 것
- PR 기반 브랜치 워크플로우를 정착시켜 팀원 브랜치를 리뷰·머지하며 게이트키핑 (`Merge pull request #95~#103` 반복 패턴)
- 컬러·타이포에 "근거 없다"는 피드백을 받고, 리서치 인사이트(형광펜=브랜드 컬러, 완독 히트맵=페르소나 페인포인트 대응)와 직접 연결해 재설계

**근거:** [2026.07.24.md](docs/meeting-notes/2026.07.24.md), `git log` PR 머지 이력, 발표스크립트 p.196 피드백 반영 내용

**레이아웃 제안:** 좌우 분할 — 왼쪽 Git 커밋/PR 타임라인 캡처("실제 개발 과정 증거"), 오른쪽 구글드라이브 폴더 구조 캡처("팀 전체 접근성 체계")
**캡션 후보:**
> 버전이 필요한 것(코드·문서)은 Git, 팀 전체가 접근해야 하는 것(영상·이미지·PRD·결정사항)은 구글드라이브로 분리해 관리했습니다.
